# Conditional key contexts

This experiment adds analysis methods with recorded key arguments. It does not redirect application callers or replace the verified Java reference tree. A successful decompilation of a context does not establish that the application ever invokes the original method with that key.

The expanded catalog contains 2,348 member records. Each was checked using the original decoder interpreted from bytecode, and the checks cover all 64 selector cases. No application classes were loaded. `reports/extended/member-catalog-validation.json` records the result.

The encoded reference key has redundant bits: for the observed 48-bit second argument `b`, the dispatcher computes `v = a ^ (b | (b << 48))`. Thus `((a >>> 48) ^ a) & 65535` equals the corresponding fingerprint of `v`. The catalog narrows possible `v` values; call-site type checks narrow them further. Agreement at at least two call sites with the same affine key expression yields a conditional argument value. This assumes the observed 48-bit model also applies at the unknown sites.

All 3,157 observed constant-key sites fit that model and match the expanded catalog. The inference found 4,114 method contexts. Applying those contexts and the expanded interpreter snapshot restored 9,233 string call sites and decoded 39,338 member references in this analysis archive; these counts include the added context copies. Thirteen reference rewrites were withheld because direct access required further proof. Runtime reachability remains unproven.

ASM BasicVerifier checked all 55,069 bodies in the expanded archive before and after string/reference restoration, with no failures. This checks stack consistency, not runtime linkage or behavior. The context transformer has 24 isolated JVM fixture checks, including constructor local/frame preservation, untouched generic methods and removal of discovery annotations from analysis copies.

Control-flow rewriting was stopped after stack-frame recomputation consumed several minutes without output. No output from that interrupted pass was adopted. Direct decompilation finished: 897 contexts have Java declarations without recorded method failures, 3,152 have recorded failures, and 26 class-write warnings also limit coverage. Java 25 parsing accepted 874 of 1,583 source units; only 15 of the 897 context declarations occur in those syntax-valid units. Those 15 exact method fragments are exported in `reference/inferred-contexts`. Remaining obfuscated names and protection guards are preserved. They are not pristine, type-checked Java or complete recovered classes.

To generate a fresh snapshot after the baseline recovery and replay this experiment:

```sh
export CLASSPATH='build/classes:.cache/deps/*'
java -Xmx5g ExtractCrypto build/recovery/keyed.jar build/crypto-expanded
bash tools/recover-inferred.sh build/recovery/keyed.jar build/crypto-expanded/crypto-state.json
```

The first command assumes `tools/build.sh` has run and the intended JDK is on PATH. The snapshot is produced by a bounded interpreter that stubs unrelated application calls; it is decoding evidence, not a faithful application initializer. The replay starts from the baseline, so aggregate decoding counts can differ from the incremental extended-pass counts above. Outputs remain under ignored `build/` and must not be launched as mods.

The syntax and fragment gates additionally require running `ParseSources` and `ExportContextFragments` on Java 25. The declaration inventory is generated by `tools/summarize_inferred.py`; failed declarations, absent class output and syntax-invalid source units are excluded from fragment export. The exact exported context keys and provenance accompany each fragment and `fragments/index.json`.
